# 아티스트·공연 찜 계정 저장

2026-11-06 로컬 구현. 운영 배포·iPhone 설치본 갱신은 별도다. 굿즈 찜·내 일정의 서버 저장은 이번 범위가 아니다.

## 동작

- 비로그인: 기존 stagepin:favorites 기기 저장을 유지한다. 손상/저장 실패는 안내하고 기존 값을 빈 데이터로 덮어쓰지 않는다.
- 로그인: 해당 회원의 찜만 서버에서 읽고 하트 변경을 서버에 저장한다. 응답 성공 뒤 화면을 갱신하며 실패를 성공처럼 보이지 않는다.
- 기기 찜 가져오기는 사용자 요청으로 메뉴·확인창·클라이언트·서버 API에서 제거했다. 기기 찜과 회원 찜은 별도이며 자동으로 합치거나 기존 데이터를 삭제하지 않는다. MY에는 모든 목록을 세로로 표시한다. [MY 구성](my-screen-ux.md) 참고.
- 로그아웃: 계정 캐시를 제거하고 기기 찜으로 전환한다. 다른 계정 로그인 시 이전 회원의 찜을 재사용하지 않는다.
- 저장 진행 중 연속 하트 입력은 중복 실행하지 않는다. 기기 간 실시간 푸시 동기화는 없으며 재조회/새로고침 시 반영된다.

## API·보안

| API | 계약 |
| --- | --- |
| GET /api/v1/favorites | 세션 회원의 {artists, concerts} 표시 스냅샷 |
| POST /api/v1/favorites | {kind: ARTIST 또는 CONCERT, id, selected, snapshot}; 해제 시 snapshot 생략 |

모든 응답은 no-store다. 소유자는 기존 StagePin 세션에서만 결정한다. 쿠키 쓰기는 정확한 웹 Origin, 네이티브는 SecureStore Bearer를 사용한다. X-StagePin-Member-Id는 소유자를 지정하는 값이 아니라 예상 회원과 실제 세션이 같은지 확인하는 사전 조건이다. 불일치/누락은 409, 비로그인은 401, 잘못된 웹 Origin은 403이다. 비동기 요청 도중 계정이 바뀌어도 다른 회원에게 의도치 않게 저장되는 것을 막는다.

운영 웹은 Vercel exact/nested favorites rewrite를 SPA fallback보다 먼저 둔다. 백엔드 V9 배포 후 프런트를 배포해야 한다. 로컬은 기존 API URL을 사용한다.

## 기술 선택과 이유

- JDBC + JSONB: 외부 MusicBrainz ID와 KOPIS 변환 UUID가 내부 artist/concert 테이블에 항상 존재하지 않으므로 카탈로그 FK를 강제하지 않았다. 회원 FK와 (member_id, kind, target_id) 유일 키로 소유권·중복을 보장한다. 전체 교체 대신 대상별 선택/해제로 다른 기기의 독립적인 찜을 지우지 않는다.
- 표시 스냅샷: 저장 당시 DTO·출처·사진 이용 정보를 보존한다. 클라이언트가 제출한 개인 데이터이므로 공식 검증 데이터로 승격하거나 다른 회원에게 공개하지 않는다. 원본 변경/URL 만료를 자동 추적하지 않으며 상세 재조회는 기존 흐름을 따른다.
- 검증·상한: 종류/ID/필수 구조/DTO 변환을 확인하고 스냅샷당 직렬화 문자열 20,000자, 회원별 총 200개로 제한한다. URL을 서버가 방문하거나 사진 파일을 복사하지 않는다.
- 트랜잭션·회원 행 잠금: 회원별 쓰기를 직렬화해 동시 추가의 quota 초과를 막는다. 단건 upsert/해제는 트랜잭션으로 처리하고 한도 오류 시 추가 전체를 롤백한다.
- TanStack Query + 기존 Context: 기존 useFavorites 화면 계약을 유지하고 회원별 query key로 서버 상태를 구분한다. 쓰기 전 진행 중 조회를 취소하고, 늦은 응답은 현재 계정과 일치할 때만 적용한다. 서버 저장을 오프라인 기기 쓰기로 조용히 대체하지 않는다.
- 기기/회원 분리: 비로그인 기기 찜을 회원 계정으로 가져오거나 자동 병합하지 않는다. 해당 기기의 기존 값은 보존한다.

## 검증 및 한계

컨트롤러 테스트: 세션 소유권, 예상 계정 불일치, 비로그인/Origin 실패 시 저장 미실행. 단위 테스트: 스냅샷/ID/크기 검증. 실제 DB 테스트: GOODS_TEST_JDBC_URL이 지정하는 새 테스트 DB의 독립 favorites_test 스키마에서 재조회·회원 분리·중복 없는 선택 갱신·quota 롤백. 사용자 DB는 사용하지 않는다.

클라이언트 테스트: 기기 데이터 유지·손상 감지·토글, 계정 전환 뒤 늦은 쓰기 차단, 저장 실패 시 성공 반영 방지, Vercel 경로 순서. 순수 함수 테스트는 React UI나 실기기 OAuth 전체 흐름을 대체하지 않는다.

계정 탈퇴·연결 해제, API 시도 제한, 굿즈 찜·일정 동기화는 별도 작업이다. 카탈로그 스냅샷을 장기간 최신 상태로 유지하는 정책도 추가 검토가 필요하다.

### 가져오기 제거 후 검증

사용자의 최종 요청으로 import API와 병합 처리를 삭제했다. 새 임시 DB에서 서버 92개 중 91개 통과·외부 AI 1개 미실행. 인증 DB 7개·굿즈 DB 4개·찜 DB 3개는 skip 없이 실행했다. 단건 선택/해제, 회원 분리, 중복 없는 스냅샷 갱신, quota 실패 롤백을 유지한다. 기존 기기/회원 찜은 삭제하지 않았다.

### 2026-11-06 최초 구현 실행 결과 (가져오기 기능 제거 전)

- 새 임시 PostgreSQL에서 전체 서버 91개 중 90개 통과, 실제 외부 모델 호출 1개 미실행. 인증 DB 7개·굿즈 DB 4개·찜 DB 3개는 skip 없이 실행했다. 찜 컨트롤러 3개·스냅샷 단위 2개도 통과했다.
- 클라이언트 lint·tsc·Node 테스트 59개·웹 export 통과. 기존 MODULE_TYPELESS_PACKAGE_JSON 경고는 남아 있으며 모듈 체계를 바꾸지는 않았다.
- 기존 로컬 DB 볼륨은 보존하고 API 컨테이너만 재빌드했다. health 200, 비로그인 favorites 401을 확인했다.
- 8081 브라우저의 기존 카카오 로그인 세션으로 공연 찜/새로고침/해제와 DAY6 찜/MY 재조회/새로고침/해제를 확인했다. 검증용으로 추가한 찜은 해제했고 기존 기기 찜 4개는 가져오거나 삭제하지 않았다.
- 실제 사용자 계정 간 전환·비로그인 UI 저장·기기 찜 가져오기 버튼은 이번 브라우저 세션에서 조작하지 않았다. 관련 소유권/병합/실패 경로는 자동 테스트로 검사했다. iPhone 실기기와 운영 배포 검증은 하지 않았다.
- 회원 찜 API·웹 반영은 이 작업 브랜치의 로컬 변경이다. main 병합이나 Render/Vercel 배포 완료를 뜻하지 않는다.
